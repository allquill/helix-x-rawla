# Deploying to Render

> Full reference, including every environment variable: [DEPLOY.md](../DEPLOY.md).

The portal runs on [Render](https://render.com) as two services, declared in
[`render.yaml`](../render.yaml). The topology is the same as the local compose
stack in `docker/portal/`:

```
internet ──▶ rawla-frontend   web service: nginx serves the app, proxies /api
                   │ private network
                   ▼
             rawla-backend    private service: the API, SQLite on a persistent disk at /data
```

Render does not run `docker-compose.yml`. The Blueprint is the equivalent, and
both services pull the same images from `docker.allquill.com`.

## Cost and limits

- **Paid instances.** `rawla-backend` needs a paid instance type (Starter or
  above), because Render attaches persistent disks only to paid services.
  `rawla-frontend` can drop to `free`, but a free service sleeps after 15 idle
  minutes and the next visit waits for it to wake.
- **One backend instance.** SQLite is a single file with a single writer, so
  `rawla-backend` runs exactly one instance. A service with a disk can't scale
  out anyway.
- **Brief downtime on each deploy.** Render stops the old backend instance
  before the new one starts, so the API is unavailable for a few seconds on
  every backend deploy. That is the price of a local-disk database.

## 1. Build and push images Render can run

Render runs `linux/amd64`. An image built with `pnpm docker:build` on an Apple
Silicon Mac is `linux/arm64` only, and Render cannot start it. Build
multi-arch and push instead:

```bash
docker login docker.allquill.com          # once
TAG=0.1.0 pnpm docker:push                 # both images, amd64 + arm64, pushed
```

The first run creates a local buildx builder named `rawla-builder`, because the
default builder cannot build for two platforms. The amd64 half is emulated on a
Mac, so it takes a few minutes. Use a real version tag, not `local`: Render
pins the tag you give it.

Check the result:

```bash
docker buildx imagetools inspect docker.allquill.com/helix-x-rawla-backend:0.1.0 | grep Platform
```

## 2. Connect Render

1. **Push this repo** to GitHub, GitLab or Bitbucket. A Blueprint is read from
   a connected repo, even though the services themselves run images.
2. **Add the registry credential.** In Render, go to **Workspace Settings →
   Registry Credentials → Add**:
   - name: `allquill`, which is what `render.yaml` refers to
   - registry: `docker.allquill.com`
   - your username, and a token or password
3. **Create the Blueprint.** Go to **New → Blueprint**, pick the repo, and
   Render reads `render.yaml`. It prompts once for every `sync: false` value:

   | Key | Value |
   |---|---|
   | `GMAIL_USER` | The Gmail address that sends mail. |
   | `GMAIL_APP_PASSWORD` | A [Google App Password](https://myaccount.google.com/apppasswords), not the account password. It needs 2-Step Verification. |
   | `MAIL_FROM` | `Rajputana Rawla <that-same@gmail.com>`. Gmail rewrites any other sender. |
   | `CONTACT_TO_EMAIL` | Where Contact Us messages go. Comma-separate several. |
   | `STRIPE_SECRET_KEY` | `sk_test_…` until you take real payments. |
   | `STRIPE_WEBHOOK_SECRET` | Enter a placeholder now; step 3 gives the real one. |
   | `PORTAL_PUBLIC_URL`, `API_PUBLIC_URL` | The frontend's URL. Until you know it, use `https://rawla-frontend.onrender.com`, and fix it in step 3. |

   `JWT_SECRET`, `OAUTH_JWT_SECRET` and `DOCUMENTS_SIGNING_SECRET` are
   generated by Render. They are separate random values, which the app
   requires.

**The backend never creates its own schema.** It refuses to start on an
empty disk. For the first deploy:

  1. Set `DB_MAINTENANCE` to `true` on `rawla-backend` before the first
     deploy. The container then stays up without starting the app.
  2. Open **rawla-backend → Shell** and apply every migration, the
     framework's tables first, then the portal's:

     ```sh
     for f in /opt/migrations/helix-x/sqlite/*.sql /opt/migrations/rawla/sqlite/*.sql; do
       echo "applying $f"; sqlite3 -bail /data/helix_x.db < "$f" || break
     done
     ```

     The loop applies the files in order and stops at the first error. The
     app prints the exact list if one is missing.
  3. Set `DB_MAINTENANCE` back to `false` and save, which redeploys.

The new portal then has the two administrators, the chapters and the
navigation config and the reference values from the migrations, and no
members. Don't run `seed:sample` against it: sample data is for development
databases only. The full guide, including upgrades and troubleshooting, is
[`apps/backend/migrations/README.md`](../apps/backend/migrations/README.md).

The frontend's health check passes once nginx is serving.

## 3. After the first deploy

1. **Set the public URLs.** Copy `rawla-frontend`'s URL from its dashboard,
   or use your custom domain. Set it as both `PORTAL_PUBLIC_URL` and
   `API_PUBLIC_URL` on `rawla-backend`, then save, which redeploys. Emailed
   verification and reset links, and Stripe's return URL, are built from these.
2. **Add the Stripe webhook.** In the Stripe dashboard, go to **Developers →
   Webhooks → Add endpoint**:
   - URL: `https://<frontend URL>/api/payments/stripe/webhook`. It goes
     through nginx to the private backend.
   - event: `checkout.session.completed`

   Put the endpoint's signing secret (`whsec_…`) in `STRIPE_WEBHOOK_SECRET`.
   Dues settle only when this signed webhook arrives.
3. **Make yourself an administrator.**
   1. Join through `/join` and verify your email, so the account exists.
   2. Open **rawla-backend → Shell** and run the grant below. The image has no
      `sqlite3`, so it goes through the app's own `better-sqlite3` driver:

      ```bash
      node -e "
      const db = require('better-sqlite3')(process.env.DB_PATH);
      const r = db.prepare(\"INSERT OR IGNORE INTO user_roles (user_id, role_id) SELECT u.id, r.id FROM users u, roles r WHERE u.email = lower(?) AND r.name = 'super_admin'\").run(process.argv[1]);
      console.log(r.changes ? 'granted super_admin to ' + process.argv[1] : 'nothing changed: no such user, or already super_admin');
      " you@example.com
      ```

   `super_admin` holds every permission the migrations create. Sign out and
   back in afterwards, because roles are baked into the JWT at login.

## Upgrading

```bash
TAG=0.2.0 pnpm docker:push
```

If the release adds migrations, apply them **before** switching the image.
Additive migrations are safe for the running version: in the backend's Shell,
apply each new file by its full name, e.g.
`sqlite3 -bail /data/helix_x.db < /opt/migrations/rawla/sqlite/0003_x.sql`. The
old image doesn't contain a file that's newer than it, so paste that file's
SQL into `sqlite3 -bail /data/helix_x.db` instead. Then bump both `image.url` tags in
`render.yaml` and commit. The Blueprint syncs and redeploys. The new backend
checks `schema_migrations` and refuses to start if a migration is missing,
from either track. A new image whose `@helix-x/backend` adds a framework
migration counts: apply that one the same way first.

## Backups and data

- **Snapshots.** Render snapshots the disk daily, and you can restore from
  **rawla-backend → Disks**.
- **Manual copy.** For a copy you hold yourself, copy `/data/helix_x.db` out
  through the backend's Shell tab.
- **Uploaded documents share the disk.** They are files under
  `/data/documents`, and the database holds only their metadata, so restore
  the two together. The 1 GB disk fills quickly with uploads of up to 50 MB
  each: grow it under **rawla-backend → Disks**, or move the files to a
  bucket with `DOCUMENTS_STORAGE_DRIVER=s3` and the `DOCUMENTS_S3_*` keys
  ([DEPLOY.md §9.2](../DEPLOY.md#92-backend-runtime)).
- **Never delete the disk.** Deleting the disk, or the `rawla-backend`
  service, deletes the database and every uploaded document.

## Why the images needed changes for Render

- **Backend.** The entrypoint starts as root, makes the directory of
  `DB_PATH` and the documents directory writable by `node`, then drops to `node` before anything else
  runs. Render's disk mounts root-owned, and SQLite running as `node` would
  otherwise fail with "unable to open database file".
- **Frontend.** nginx listens on `$PORT`: 80 by default, and 10000 as Render
  sets it. It also accepts `BACKEND_UPSTREAM` as a bare `host:port`, which is
  what Render's private address looks like, adding the `http://` itself.
- **`TRUST_PROXY=2`.** Requests pass Render's edge, then nginx. The API reads
  the client IP two hops back, so the contact form's per-IP limit counts real
  visitors. Locally, behind nginx alone, it is `1`.
